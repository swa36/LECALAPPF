# Метка «архив» у товара и снятие с площадок

**Дата:** 2026-07-28

## Проблема

Товар, перенесённый в 1С в группу «Удалено(архив)», перестаёт приходить в
`/products`. Синхронизация умеет только создавать и обновлять, поэтому на сайте
он остаётся с замороженным остатком и продолжает продаваться: попадает в фиды
Ali и Avito, остатки уезжают на WB и Ozon.

На проде таких товаров 731, из них 465 с ненулевым остатком и 529 с живой
карточкой на WB.

Группа «Удалено(архив)» в `/categories` тоже не приходит, поэтому определить
архивность по родителю нельзя.

## Решение

Единая метка `Product.is_archive`. Источник метки может меняться, всё, что ниже
по течению, работает от флага.

### 1. Поле

```python
# catalog/models.py, Product
is_archive = models.BooleanField(
    default=False, db_index=True,
    verbose_name='Архив (нет в выгрузке 1С)'
)
```

Индекс нужен: по полю фильтруются фиды при каждой генерации. В админке — колонка
и фильтр.

### 2. Простановка при синхронизации

`catalog.tasks.archive_missing_products` за один вызов делает два прохода:

- товара нет в выгрузке → `is_archive=True`, `stock=0`;
- товар есть в выгрузке и помечен → `is_archive=False`, остаток приедет из 1С сам.

Защита: если выгрузка вернула меньше половины каталога, не трогаем ничего —
это похоже на сбой обмена, а не на чистку в 1С. Обе операции пишутся в
`logs/archived_1c.log`.

Вызывается из `get_data_1C` сразу после `get_all_products()`.

### 3. Фиды Ali и Avito

В `src/lekala_class/class_feed.py`, `CreatorFeed.create_items` к фильтру
добавляется `& Q(is_archive=False)`. Одна точка — оба фида строятся этим методом.

Фильтр `stock__gt=0` там уже есть, и архивные выпали бы и без флага, но явная
метка не сломается, если остаток кто-то проставит руками.

### 4. Перенос карточек в корзину WB

Команда `python manage.py trash_archived_wb` (`--apply` для выполнения):

1. берёт `Product.objects.filter(is_archive=True, wb__isnull=False)`;
2. запрашивает текущую корзину через `WBItemCard.get_trash()` и исключает те
   `nmID`, что уже там — иначе повторный прогон слал бы одно и то же;
3. без `--apply` печатает список: `nmID`, артикул, название;
4. с `--apply` шлёт `del_item()` (`v2/cards/delete/trash`) пачками с паузой под
   лимит 3 запроса в минуту.

Запуск ручной: на первом прогоне под перенос попадает ~529 карточек, их нужно
просмотреть глазами. Восстановление из корзины не автоматизируем — карточки
возвращаются вручную через `v2/cards/recover`.

Карточка продаётся, пока по ней есть остатки, поэтому обнуление остатка из п.2
обязательно и происходит раньше.

### 5. Задел под `deletion_mark`

Когда 1С начнёт отдавать признак пометки на удаление, появится второй источник
метки. Код пишется сразу:

```python
# GetData1C.set_catalog_data_stock
deletion_mark = item.get("deletion_mark")
if deletion_mark is not None:
    defaults["is_archive"] = bool(deletion_mark)
    if deletion_mark:
        defaults["stock"] = 0
```

Пока поля нет, `.get()` возвращает `None` и ветка не работает — поведение не
меняется. Появится поле — заработает без правок.

Источники не конфликтуют:

| Ситуация | Кто ставит метку |
|---|---|
| Товара нет в выгрузке | `archive_missing_products` |
| Товар в выгрузке с `deletion_mark: true` | `set_catalog_data_stock` |

**Требования к 1С-специалисту:**

- поле `deletion_mark`, boolean, в `snake_case` как остальные;
- то же поле в `/categories` — тогда `prune_categories` будет читать признак
  напрямую вместо вывода «кого нет в выгрузке»;
- помеченные товары должны **начать приходить** в `/products`, а не скрываться,
  иначе поле бессмысленно.

## Поток

Одна синхронизация: архивные получают метку и нулевой остаток →
`update_remains_wb`, `update_remains_ozon`, `update_stock_ali` разносят ноль по
площадкам → из фидов Ali и Avito товары исчезают → карточки WB переносятся в
корзину отдельной командой.

## Решения, принятые явно

- **Флаг и обнуление остатка вместе.** Ozon отдельной обработки не требует:
  нулевой остаток снимает товар с продажи там же.
- **Метка снимается автоматически, карточка WB восстанавливается вручную.**
  У `v2/cards/recover` лимит 3 запроса в минуту, и автовозврат может вскрыть
  карточку не вовремя.
- **Перенос в корзину — ручной запуск с dry-run.** Автоматический перенос в
  `after_catalog_update` означал бы, что любая ошибка в 1С сразу увозит карточки
  в корзину, откуда WB чистит их через 30 дней.

## Не входит

- Физическое удаление товаров из базы. `prune_products` остаётся диагностикой:
  архивные и так уходят с площадок.
- Автоматическое восстановление карточек WB из корзины.
- Обработка архивных категорий — у `prune_categories` свой механизм.
